## Findings

### 1. Major — Percent-encoded path data can become a query and target the wrong resource

File: [server/api/arbiter/[...].ts:20](</D:/claude/llmArbiter-proxy/server/api/arbiter/[...].ts:20>), [server/utils/proxyPolicy.ts:133](</D:/claude/llmArbiter-proxy/server/utils/proxyPolicy.ts:133>)

Why it is wrong: h3 does not actually use `decodeURI` semantics. ufo protects `%2F`, but decodes `%3F` with `decodeURIComponent`. The router subsequently treats that decoded `?` as the query delimiter before `getRouterParam` runs. The validator therefore never sees the part after `%3F`. Separately, h3 deliberately retains `%25`, while the validator’s `decodeURI(parsed.pathname)` changes it to `%`, causing legitimate percent signs to fail the identity check.

Concrete failing scenarios:

- `useApi().updateRule('a?b', value)` sends `PATCH /api/arbiter/config/rules/a%3Fb`. h3 turns this into `/api/arbiter/config/rules/a?b`; the wildcard becomes `config/rules/a`, and the proxy contacts `/config/rules/a?b=`. If the backend ignores the query, the mutation updates rule `a`, not `a?b`.
- `useApi().updateRule('rate%limit', value)` sends `rate%25limit`. h3 retains `%25`, but the round-trip comparison decodes it, so the proxy returns 404 although the path was correctly produced with `encodeURIComponent`.

### 2. Major — Refused redirect bodies are never cancelled

File: [server/utils/proxyHandler.ts:162](</D:/claude/llmArbiter-proxy/server/utils/proxyHandler.ts:162>)

Why it is wrong: manual fetch returns a live response body for a 301/302/307/308 that contains one. `runProxy` returns its 502 without consuming or cancelling that stream. The `pipeline` cancellation fix only runs for accepted responses. The underlying upstream connection can consequently remain occupied until garbage collection or the 30-second signal fires.

Concrete failing scenario: the upstream returns `302 Location: https://attacker.example/` and then continuously streams a chunked body. Each authenticated request receives a prompt 502, but leaves an upstream response/socket alive for up to 30 seconds. Repetition can exhaust the upstream connection pool. The redirect unit mocks all use `body: null`, so they conceal this behavior.

### 3. Major — The new E2E layer still permits security-critical shell regressions to pass

File: [tests/e2e/proxy.e2e.test.ts:105](</D:/claude/llmArbiter-proxy/tests/e2e/proxy.e2e.test.ts:105>), [tests/e2e/proxy.e2e.test.ts:183](</D:/claude/llmArbiter-proxy/tests/e2e/proxy.e2e.test.ts:183>), [tests/proxyHandler.test.ts:322](</D:/claude/llmArbiter-proxy/tests/proxyHandler.test.ts:322>)

Why it is wrong: the E2E upstream always returns 200, every E2E proxy call is authenticated and GET-only, and successful tests never inspect the body received by the browser. The injected redirect tests directly return a 3xx, thereby assuming the shell’s fetch configuration has already prevented following it.

Concrete failing scenarios that leave all current tests green:

- Remove `redirect: 'manual'`; the E2E upstream never redirects, while the injected test still supplies a 302 directly. Production again follows a cross-origin redirect with `X-API-Key`.
- Wire `getSessionUser` in the shell to always return a truthy value; unit tests still verify only the injected core, and E2E requests are already authenticated. Anonymous upstream access is unobserved.
- Replace the pipeline with `event.node.res.end()` after the upstream call. Status, upstream URL, and upstream-header assertions still pass even though every browser response body is discarded.
- Wire `readBody` to return `undefined`; all E2E requests are GET, so bodyless POST/PATCH/DELETE mutations are not detected.

### 4. Minor — E2E application-port allocation has a bind race

File: [tests/e2e/proxy.e2e.test.ts:49](</D:/claude/llmArbiter-proxy/tests/e2e/proxy.e2e.test.ts:49>), [tests/e2e/proxy.e2e.test.ts:116](</D:/claude/llmArbiter-proxy/tests/e2e/proxy.e2e.test.ts:116>)

Why it is wrong: `reservePort` closes its listener before spawning the application. The port is therefore unreserved during the interval in which the child starts.

Concrete failing scenario: another process or parallel CI worker binds the selected port after line 62 and before the child reaches `listen()`. The application exits with `EADDRINUSE`, while `waitForApp` polls for up to 60 seconds before failing.
