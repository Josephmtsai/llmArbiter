Auto Optimizer 流程總覽

四張圖從不同高度看同一件事：測試案例（eval pool）怎麼被切分與取用、一次 optimizer run 的骨幹、每一輪候選 prompt 必須通過的三道 gate，以及各角色之間的訊息往返。

Fig. 1 · Sankey

測試案例的流向：12,000 筆裡只有 600 筆會被評分

帶寬等於案例數。訓練集只用於重新標記與人工審核，optimizer 從未拿它評分；驗證快照每輪重複使用，測試快照只在迴圈結束後使用一次。

資料池與切分

  • 來源：LogChunks、Travis CI、BGL、HPC 硬體日誌，經 generate_eval_pool_from_logs.py 產生 12,000 筆，五種 action 各 2,400 筆。
  • 切分固定 60 / 20 / 20；共用 split_group 的近似重複案例會落在同一切分，避免跨界洩漏。
  • relabel_eval_pool.py 以較強模型重標；confidence < 0.8 進入 review queue，人工 confirm / correct / reject 後才回到池中。

驗證快照（每輪評分）

  • run 開始時從 val split 每 action 抽 40 筆，共 200 筆，寫入 val_snapshot_ids。
  • baseline 與每一輪候選都用同一組 200 筆，跨輪 accuracy 才能直接比較。
  • round accuracy 與 accuracy_delta 都是「這 200 筆」的表現，不是整池。

測試快照（最終驗收）

  • 迴圈結束後從 test split 每 action 抽 80 筆，共 400 筆，只評分一次。
  • optimizer 在整個 run 期間從未看過 test split，test_accuracy 是無偏的泛化估計。
  • 驗證準確率 ≠ 測試準確率，兩者要分開解讀。

一次 optimizer run 的骨幹

從 POST /optimizer/run 到 operator 手動啟用。每一輪的細節（候選生成與三道 gate）展開在 Fig. 3。

Fig. 3 · Flowchart · Round level

每一輪的三道 gate：候選 prompt 怎麼變成 kept / rejected / skipped

G0 在評分前擋掉結構不合法的候選；G1 要求整體驗證準確率進步；G2 要求受保護的 action 不能退步超過容差。三道全過才 kept。

G0 · 結構驗證（評分前）

  • 候選必須是可解析的結構化物件，含必要欄位、所有分類 action，以及 JSON 輸出指令。
  • 不合法時後端先重試一次；再失敗才記錄 skip_reason，該輪 kept=false、eval_run_id=null。
  • 常見原因：optimizer-candidate-invalid-json、-missing-actions:<action>、-missing-json-contract、-missing-fields:<field>、-unsupported-actions:<action>。
  • Skipped 不代表 prompt 變差，只代表這一輪沒有候選被測試；但仍計入 max_rounds。

G1 · 整體準確率

  • overall_pass = round_accuracy > previous_best_accuracy，在同一組 200 筆驗證快照上比較。
  • 未通過時 reject_reason 記為 no overall improvement，是最常見的拒絕原因。
  • previous_best 是上一個 kept 的候選，若尚無 kept 則是 baseline。

G2 · 各動作回退容差

ActionTolerance
notify_human±2%
send_email±2%
trigger_rebuild±5%
trigger_fallback±5%
trigger_restart±5%
  • action_pass = action_delta ≥ −tolerance；僅在該 action 的 baseline 樣本數 ≥ 10 時生效。
  • 整體有進步也會被拒：關鍵 action 退步會讓真實事件繞過人工升級。

Fig. 4 · Sequence

一次 run 的訊息往返：誰負責分析、誰負責評分、誰負責留下紀錄

Optimizer LLM 與 Evaluator 是兩個不同的模型：前者只讀失敗樣本並改寫 prompt，後者只對 200 / 400 筆案例出題評分。所有輪次資料寫入 PostgreSQL。

角色分工

  • Evaluator：目前 active provider（ollama / claude / codex / openrouter / nvidia），每個案例一次 LLM 呼叫，Semaphore(10) 併發，回傳 accuracy、failing_cases、confusion_matrix、per_action_metrics。
  • Optimizer LLM：OPTIMIZER_MODEL（OpenRouter，預設 deepseek/deepseek-v3），只負責分析失敗與改寫 prompt，必須與 Evaluator 不同模型。
  • Optimizer 生成的 PromptVersion 一律 is_active=false，label 為 optimizer-round-N。

持久化（PostgreSQL）

  • optimizer_runs：status、模型、baseline_accuracy、val_snapshot_ids、test_accuracy、finished_at。
  • optimizer_rounds：accuracy、kept、confusion_matrix、analysis_text、per_action_deltas、reject_reason / skip_reason。
  • optimizer_round_failures：每輪最多 50 筆失敗樣本，含 log_snippet 與 hardware_info。
  • service 重啟後所有 run 紀錄完整保留。

Operator 端的兩個閘

  • GET /optimizer/history 看 val accuracy 趨勢、confusion 是否收斂、test_accuracy 是否跟上。
  • 只有 PATCH /prompts/{id}/activate 會改變生產用的 active prompt；optimizer 本身不會自動啟用。
  • DELETE /optimizer/runs/{id} 可取消進行中的 run；review queue 則守住標記品質這一端。
